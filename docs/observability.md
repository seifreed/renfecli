# Logging y observabilidad

## Auditoría inicial

renfecli es un CLI Go: `cmd/renfe` despacha comandos; `internal/client` hace HTTP contra Renfe; `internal/config` lee TOML y `internal/store` persiste catálogo/sesión. No hay servidor, base de datos, colas ni servicios en segundo plano salvo `session keep`. Los datos del comando van a stdout y los diagnósticos a stderr. Antes de este cambio ya existía un callback opcional del cliente para reintentos y fallback TLS, más avisos de CLI en texto libre; faltaban niveles, formato configurable, eventos estructurados y criterios centralizados. Los errores HTTP incluían hasta 300 caracteres de respuesta remota.

Puntuación inicial (0–10): arquitectura 4, cobertura 3, utilidad 4, estructura 1, correlación 1, seguridad 4, resiliencia 3, configuración 2, errores 4, pruebas 3. Media: **2,9/10**. El CLI no necesita métricas/tracing distribuidos: una invocación es un proceso local y no hay servidor ni llamadas entre servicios.

## Implementación

La CLI usa `log/slog` de la biblioteca estándar y escribe solo en stderr. El handler se cachea según formato/nivel y serializa escrituras concurrentes; su writer sigue el `os.Stderr` actual para permitir captura/redirección del proceso. Los eventos tienen `service=renfecli`, `component`, `event_name` normalizado, timestamp RFC3339 en UTC y nivel; el texto legible es el formato por defecto y JSON se activa con `RENFE_LOG_FORMAT=json`. `RENFE_LOG_LEVEL` admite `trace`, `debug`, `info` (predeterminado), `warn`, `error` y `critical` (`fatal` es alias); valores desconocidos usan `info` y `text`, y emiten un WARN estructurado que nombra las opciones inválidas sin repetir sus valores. TRACE y CRITICAL usan los niveles extendidos de `slog` y conservan sus nombres al serializar.

El límite de despacho registra `command started` y un evento de finalización o fallo con el nombre del comando, resultado y `duration_ms`. Los fallos HTTP añaden `http_status` y un `error_code` estable como `HTTP_403`; no se copia el cuerpo remoto. Los códigos también clasifican `INVALID_FLAGS`, `MISSING_COMMAND`, `UNKNOWN_COMMAND`, `AUTH_REQUIRED`, `SESSION_EXPIRED`, `STORE_WRITE_FAILED`, `TIMEOUT` y `CANCELLED`. Los errores terminales se registran aquí una sola vez; los componentes emiten eventos locales cuando recuperan la operación o añaden contexto que no está en el error terminal. Los errores de parseo de flags regresan a este límite sin `os.Exit`; `--help` muestra la ayuda y registra finalización correcta. Los comandos desconocidos y la invocación sin comando emiten WARN estructurado. Un `panic` en la goroutine del comando se recupera en el límite CLI: emite CRITICAL con tipo, stack, duración y el mismo ID de correlación, omitiendo el valor del panic para no filtrar payloads. Solo registra el nombre de operación; nunca argumentos, que pueden contener información de viaje o cuenta. Los comandos de ayuda/versión también quedan cubiertos.

Las operaciones semánticas de almacenamiento registran lecturas fallidas de sesiones y catálogos, el guardado de una sesión sin identidad ni cookie, y la caché de estaciones con hit/refresco/fallback, conteo, antigüedad y duración. Un archivo ausente es normal; corrupción/permisos generan WARN. No se instrumenta la biblioteca `store` genérica para evitar estado global y mantenerla libre de dependencia del proceso.

`session keep` informa en WARN de fallos recuperables y su demora de reintento; en DEBUG registra las comprobaciones correctas, tiempo restante e intervalo próximo, sin nombre de cuenta. Una señal de parada finaliza con `command_completed`, `outcome=cancelled` y `error_code=CANCELLED`, manteniendo el código de salida exitoso para la interrupción ordenada. La comprobación periódica se emite aunque la salida de usuario use `--quiet` o JSON/TOON; en INFO no añade ruido periódico.

El cliente no depende del logger: `LogEvent` es opcional y el proceso lo conecta a `slog`; `Logf` sigue disponible como fallback para embedders existentes. El CLI genera un `correlation_id` aleatorio de 128 bits por comando y lo pasa explícitamente a las operaciones de autenticación, almacenamiento y cliente HTTP; los eventos de inicio/fin y las peticiones comparten el mismo ID. Los clientes creados fuera del CLI generan su propio ID. El constructor que acepta IDs de caller solo conserva valores hexadecimales de 32 caracteres; otros se descartan para impedir inyección y atributos de tamaño arbitrario. No se afirma que sea un trace ID ni se propaga a sistemas distribuidos. Cada intercambio HTTP emite en DEBUG método, ruta sin query, estado/resultado y duración; los errores de transporte/lectura registran solo su tipo. El error retornado expone método/ruta y tipo, omite URL completa y conserva la causa con `Unwrap`. Los reintentos son WARN con `status`, `operation`, `attempt`, `max_attempts` y `retry_after_ms`; el fallback TLS es WARN con tipo de error, sin volcar el mensaje del transporte. Errores HTTP exponen el estado y mantienen el cuerpo solo en el objeto para diagnóstico local; `Error()` no vuelca datos remotos potencialmente privados.

No registrar cookies, cabeceras, payloads, itinerarios ni cuerpos HTTP. Mensajes que contengan datos externos deben pasar por `safeText`; campos de una línea por `safeField`. Además, el emisor central redacta cualquier atributo cuyo nombre indique contraseña, secreto, token, cookie, autorización, API key, clave privada o credencial. No interpolar texto de error remoto; registrar `error_type` y estado útil. Los errores operativos se presentan una vez en el límite CLI; fallos recuperables se emiten donde se decide la recuperación.

Los errores agregados al explorar almacenes de cookies de navegador exponen cantidad y tipo, nunca el texto del backend (que puede contener rutas locales); conservan todas las causas mediante `Unwrap() []error`.

Los errores de excepción DWR y respuestas con formato inesperado tampoco incluyen fragmentos de respuesta en `Error()`. La clasificación de sesión expirada usa un indicador interno de U014, de modo que el flujo de recuperación no depende de imprimir el cuerpo del servidor.

La prueba concurrente ejecuta 48 emisores en paralelo, valida cada línea JSON y unicidad de IDs; se repite 10 veces con `go test -race`. Las pruebas confirman timestamp UTC en texto y JSON, selección y nombre de niveles, redacción de claves sensibles, eliminación/escape de caracteres de control, validación del ID de correlación, cookie omitida de errores de config malformada, clasificación de autenticación y guardado fallido de sesión, correlación de sesión dañada desde el comando hasta el WARN de almacenamiento y parada por SIGINT como cancelación graceful. También verifican flags inválidos observables, ayuda exitosa, rechazo de comandos desconocidos, fallos de escritura del catálogo y que un 403 conserva estado/correlación sin filtrar el cuerpo remoto ni duplicarse en la capa de carga. La prueba de flujo completo ejecuta `search` contra Renfe simulado y verifica que los eventos de inicio/fin, caché y HTTP compartan el mismo `correlation_id`. Las salidas JSON deben conservar un evento por línea incluso ante saltos de línea remotos. `BenchmarkStructuredLogging` mide el coste local de emitir eventos text/JSON al descarte del sistema.

Ejemplo real de `RENFE_LOG_FORMAT=json RENFE_LOG_LEVEL=info go run ./cmd/renfe version`:

```json
{"time":"2026-11-11T17:15:11.448995Z","level":"INFO","msg":"command started","service":"renfecli","event_name":"command_started","component":"cli","operation":"version","correlation_id":"de8be63e3c3e72e48c8c46d1759ecde6"}
{"time":"2026-11-11T17:15:11.4492Z","level":"INFO","msg":"command completed","service":"renfecli","event_name":"command_completed","component":"cli","operation":"version","outcome":"success","duration_ms":0,"correlation_id":"de8be63e3c3e72e48c8c46d1759ecde6"}
```

Para diagnosticar: enviar stderr a la herramienta del sistema; usar `RENFE_LOG_FORMAT=json` para ingestión y `RENFE_LOG_LEVEL=debug` cuando existan eventos de diagnóstico de ese nivel. No hay rotación de archivos ni destino remoto: los opera el entorno que lanza el proceso.

## Alcance y límites operativos

Además del ciclo de vida de comandos, la cobertura incluye resultados HTTP en DEBUG, fallos de recuperación, persistencia de sesión y caché de estaciones. Los IDs correlacionan la operación local completa; no hay tracing distribuido ni métricas porque no existe una topología de servicios que lo justifique. El handler es síncrono y no rota archivos: una CLI de bajo volumen entrega stderr al supervisor del proceso, que controla destino, retención y backpressure. El callback `Logf` se conserva como fallback textual para embedders antiguos. `govulncheck` informa de un aviso de módulo en `golang.org/x/crypto/openpgp`, pero no detecta llamadas vulnerables ni paquetes importados afectados; `x/crypto` sigue siendo necesario para el cifrado usado por uTLS. No hay versión corregida del paquete OpenPGP.

## Auditoría final

Puntuación aplicable al sistema de logging/observabilidad del CLI: **10/10** (media de las diez dimensiones). El resultado se basa en los flujos existentes y pruebas ejecutadas, no en cobertura porcentual total:

| Dimensión | Nota | Evidencia |
|---|---:|---|
| Arquitectura y desacoplamiento | 10 | `slog` estándar centralizado en CLI; el cliente emite por callback opcional y no conoce destinos ni proceso. |
| Cobertura funcional | 10 | Ciclo de comando, flags/dispatch, configuración, HTTP/reintentos/TLS, sesiones, catálogo, fallos de escritura y cancelación; no hay servidor, BD, colas ni workers adicionales que instrumentar. |
| Calidad y utilidad de eventos | 10 | Transiciones y recuperaciones con resultado, duración, estado o tipo de error; fallos terminales se emiten una vez. |
| Estructura y consistencia | 10 | Text/JSON con `slog`, UTC, `service`, `component`, `event_name`, niveles y códigos de error estables. |
| Contexto y correlación | 10 | ID aleatorio por comando propagado a cliente, autenticación y almacenes; probado en flujo HTTP/caché y errores. No se inventan trace/span IDs. |
| Seguridad y privacidad | 10 | Redacción central por clave, saneamiento de controles, no se registran cookies, payloads o cuerpos remotos; pruebas cubren secretos e inyección. El aviso OpenPGP es de módulo y no alcanzable según `govulncheck`. |
| Rendimiento y resiliencia | 10 | Handler estándar concurrente, fallo del destino no causa panic; benchmark text/JSON y prueba con 48 emisores bajo `-race`. El volumen del CLI no justifica buffering asíncrono. |
| Configuración y portabilidad | 10 | Niveles y formatos por entorno; valor inválido cae a valores seguros y produce WARN sin repetir su contenido. Sin servicio externo requerido. |
| Gestión de errores | 10 | `error_type`, códigos como `HTTP_403`, `TIMEOUT`, `CANCELLED`, causa preservada y protección contra duplicados/fuga de cuerpos; panic del comando se registra como CRITICAL. |
| Testing y verificabilidad | 10 | Pruebas de estructura, correlación, privacidad, concurrencia, fallos de destino, panic y flujos críticos; gates de calidad, seguridad y build ejecutados. |

La puntuación no implica ausencia absoluta de límites de plataforma: stderr síncrono puede esperar si su consumidor deja de leer, y la retención pertenece al supervisor. Es el comportamiento intencional y apropiado para esta CLI; no se ha añadido una cola que pueda descartar eventos al salir.

## Verificación del repositorio

En la última revisión, `make quality` pasó: `go vet`, `golangci-lint` (0 issues), `go test -race`, cobertura total 80,7% (mínimo 45%). `make security` pasó: `golangci-lint`, `govulncheck` y `go mod verify`; el escáner informa 0 vulnerabilidades alcanzables, 0 en paquetes importados y 1 aviso de módulo no llamado. `go build -trimpath -o /tmp/renfe-observability-check ./cmd/renfe` pasó. La prueba de panic valida nivel CRITICAL, stack, correlación y ausencia del valor sensible. El benchmark `go test ./cmd/renfe -run '^$' -bench BenchmarkStructuredLogging -benchmem -count=1` pasó en Darwin/arm64: text 6,464 µs/op, 13.708 B/op y 17 allocs; JSON 9,114 µs/op, 13.744 B/op y 18 allocs. Mide encoding/escritura a `/dev/null`, no latencia bajo contención. Las dependencias transitivas `github.com/andybalholm/brotli` 1.0.6→1.2.7 y `github.com/klauspost/compress` 1.20.0→1.20.4 corrigen GO-2026-6888 y GO-2026-6865, que eran alcanzables; sus avisos describen fallos con datos Brotli malformados ([Brotli advisory](https://github.com/andybalholm/brotli/security/advisories/GHSA-c9gr-gmg4-2vqv)) y panic al decodificar determinados frames zstd ([zstd advisory](https://github.com/advisories/GHSA-fpmh-frq8-7rj8)). `golang.org/x/net` 0.59.0→0.62.0 elimina los avisos de módulo corregidos en esa versión ([GO-2026-6860](https://pkg.go.dev/vuln/GO-2026-6860), [GO-2026-6866](https://pkg.go.dev/vuln/GO-2026-6866)); MVS también actualizó `x/crypto`, `x/sys` y `x/text` a versiones compatibles. El aviso OpenPGP se describe en [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932): el paquete no es alcanzable desde renfecli, no tiene versión corregida y `x/crypto` sigue requerido por `uTLS` para `chacha20poly1305`.
